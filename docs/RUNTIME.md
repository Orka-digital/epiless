# Worker limits and verification boundary

Reviewed on 2026-10-27. This is a deployment constraint review, not a production CPU or memory benchmark.

## Platform limits

Cloudflare currently documents the following limits. CPU time excludes waiting for network and database requests. Memory is shared by concurrent requests in one isolate. [Official Workers limits](https://developers.cloudflare.com/workers/platform/limits/)

| Constraint        | Free                | Paid                                                |
| ----------------- | ------------------- | --------------------------------------------------- |
| HTTP CPU time     | 10 ms per request   | 30 seconds by default, configurable up to 5 minutes |
| Memory            | 128 MB per isolate  | 128 MB per isolate                                  |
| Worker bundle     | 64 MiB uncompressed | 64 MiB uncompressed                                 |
| Startup execution | 1 second            | 1 second                                            |

The generated deployment configuration selects **100 ms CPU per request** and assumes Paid Workers. This is an initial cost guard, not evidence that every operation fits it. Authentication uses Better Auth's maintained password hashing; never weaken hashing to meet a cheaper CPU budget. Change the deployment limit only after measuring realistic successful and rejected authentication, maximum-size uploads, validation and publication requests.

## Evidence from this implementation

- An isolated source copy, without `.dev.vars`, `.env` files or local D1 state, completed `astro check` and `astro build`. The check reported zero errors, warnings or hints. Build-time secrets and a provisioned database are not required for those CI steps.
- The initial development bundle, before the later P0 additions, had an isolated `wrangler deploy --dry-run` result of **2,980.82 KiB total upload** and **649.68 KiB gzip**. This is historical bundle evidence, not the current bundle size or runtime heap usage. No Worker was uploaded or deployed by that command.
- Account lists query metadata rather than entire report payloads. Anonymous requests without cookies bypass auth initialization. Report reads apply access predicates in SQL before returning payloads.
- Report JSON is bounded at 1 MiB; application request readers stop oversized streams. These bounds reduce amplification but do not prove aggregate memory usage under concurrent requests.

No deployed `startup_time_ms`, p95/p99 CPU, heap peak or production cost result has been measured. Local browser latency and green CI are not substitutes for those measurements. Before opening the hosted service, test the configured 100 ms cap in staging, record resource-limit failures and memory under concurrent login/upload requests, and confirm the expected monthly budget. Report/index reads must remain independent of Turnstile availability.

## Static headers and caching

[`public/_headers`](../apps/web/public/_headers) protects direct Static Asset responses. Cloudflare does not apply that file to responses generated by Worker code; [`src/middleware.ts`](../apps/web/src/middleware.ts) provides those headers for SSR/API responses. Astro's generated CSP contains the exact script/style hashes, while the separate header forbids embedding. [Cloudflare Static Asset headers](https://developers.cloudflare.com/workers/static-assets/headers/)

Only fingerprinted `/_astro/*` assets receive a one-year immutable browser cache. Static HTML and fixed-name assets keep the platform's revalidation default. Dynamic account, index and report responses use `private, no-store`. The independently hosted signed rule feed has its own R2/CDN policy and must not inherit an interactive challenge or account requirement from the app.
